\subsection{Description of Workflow Steps}
\label{sec:workflow-steps}

\begin{enumerate}

    \item \textbf{Project load.} When a project is opened, the plugin builds one
    client for it. The client creates, configures and loads its twin:
    \begin{verbatim}
client = HydrologicalTwinClient.build(
    metadata,
    configure_kwargs=configure_kwargs,
    load_kwargs={"geo_provider": geo_provider},
)
    \end{verbatim}
    \texttt{load} builds each compartment from the layers the plugin's layer
    provider serves, and decodes the \cw\ binary outputs into the NumPy cache.

    \item \textbf{Dialog.} When the user runs a dialog (for example,
    "Compare Sim/Obs"), the dialog calls one client method, such as
    \texttt{compare\_sim\_obs}, with the options the user chose.

    \item \textbf{Client.} The method chains the verbs the operation needs,
    typically \texttt{fetch}, then \texttt{transform}, then \texttt{render} or
    \texttt{export}, each with its \texttt{kind}.

    \item \textbf{Façade.} \texttt{HydrologicalTwin} checks that the twin is
    \texttt{LOADED}, builds the request, and routes it on its \texttt{kind}
    through \texttt{dispatch.py}.

    \item \textbf{Services.} \texttt{Temporal} reads the cache and the
    observation files and aggregates in time; \texttt{Budget} computes
    budgets; \texttt{Spatial} finds catchment and outcropping cells;
    \texttt{Operator} and \texttt{Comparator} compute; \texttt{Renderer} draws
    the figures; \texttt{export} writes NumPy and GeoPackage files.

    \item \textbf{Back to the dialog.} The client returns a typed result, for
    instance a \texttt{CompareSimObsResult} with \texttt{pdf\_path} or
    \texttt{html\_path}, and the dialog displays the files it names.

\end{enumerate}

The access-control and provenance steps of the \hydrot\ target (private keys,
logged actions, verification of Git-synchronised records) are described in
Part~I; HTAS does not perform them.
