\section{Road Map}

\subsection{Restructuring Phase}

With the support of AI, the entire code base was restructured into a new backend architecture (\texttt{backendMonolithic}) built around a central \texttt{HydrologicalTwin} class.  
This class is now intended to be the main entry point for the frontend: all backend components are accessed through this object, which acts as a single, coherent interface to the simulation, data handling, and post-processing layers.

The full design discussion and refactoring rationale are documented in the following conversation:  
\url{https://chatgpt.com/share/692dc00f-ee9c-8011-8626-8c5f5eb09c92}

\subsection{Linking the Hydrological Twin to the Existing Frontend}

All frontend dialog scripts were connected to a single shared instance, \texttt{hydro\_twin}, of the \texttt{HydrologicalTwin} class.  
This instance is created once in the \texttt{ExploreData} module and retrieved by each dialog at initialization time.

This ensures that:
\begin{itemize}
    \item all dialogs operate on the same model state,
    \item no duplicated backend objects are created,
    \item simulation results, observation data, and configuration remain consistent across the GUI.
\end{itemize}

The \hydrot class is composed of several methods that recall backend functionality.  
The most frequently used ones originate from the \texttt{Manage} class.  
Dialog boxes should not directly call \texttt{Manage} methods, but instead access them through the \hydrot API.

\subsection{Backend Performance Improvements}

\subsection{Data Loading at Configuration Stage}

Data are read from binary files during the instantiation of \texttt{ExploreData}, which in CaWaQS Viz happens at the configuration stage.  
Subsequent operations only involve reading already-loaded NumPy arrays.

\paragraph{Key architectural message}
\emph{``Let’s think well together. I want these APIs to be shared functions of my dialog boxes. The goal is to have fewer APIs that can be composed together, allowing strong operations with simpler and cleaner code.}

\emph{For instance, if we consider the hydrological regime, copying all the logic into functions tied to the \texttt{Vec\_Operator} and then connecting them to the API would make the system less adaptable to other operations.}

\emph{If I fragment the APIs into too many very small tasks, does it make the concept of an API useless? And looking at the dialog boxes, which APIs should be designed to answer their shared questions?''}

\paragraph{Proposed architectural response}
To preserve composability, adaptability, and reuse across dialog boxes, the API layer should expose a small set of \textbf{orthogonal and composable primitives}. High-level analyses (e.g.\ regime computation or model--observation comparison) should be built by composing these primitives, rather than being implemented as standalone APIs.

\paragraph{Proposed composable primitives}
The following five primitives form a minimal yet expressive API foundation:

\begin{itemize}
  \item \texttt{extract\_values}  
  \begin{itemize}
    \item Extracts raw simulation values together with their associated dates.
    \item No spatial or temporal aggregation applied.
  \end{itemize}

  \item \texttt{extract\_area\_values}  
  \begin{itemize}
    \item Extracts values over a spatial subset (e.g.\ basin, mask, polygon).
    \item Reusable for any spatially dependent operation.
  \end{itemize}

  \item \texttt{apply\_temporal\_operator}  
  \begin{itemize}
    \item Applies temporal aggregation or transformation (mean, sum, regime, rolling statistics, etc.).
    \item Decouples temporal logic from data extraction.
  \end{itemize}

  \item \texttt{read\_observations}  
  \begin{itemize}
    \item Reads observational data (e.g.\ \texttt{.dat} files).
    \item Provides a unified interface between simulated and observed datasets.
  \end{itemize}

  \item \texttt{apply\_spatial\_average}  
  \begin{itemize}
    \item Performs spatial averaging or reduction.
    \item Can be combined with any extraction or temporal operator.
  \end{itemize}
\end{itemize}

\subsection{Config problem in SteadyState : QGIS closes completely}. 
    \begin{itemize}
    \item When configuring a project in steady-state mode, CaWaQS does not produce a HYD corresp file.txt. During initialization, when the plugin builds the HYD compartment mesh, it tries to read this file and calls sys.exit() if it's missing. In a QGIS plugin, sys.exit() doesn't just stop the plugin — it raises SystemExit which propagates through QGIS's C++ event loop and kills the entire application.The correspondence file maps GIS cell IDs to CaWaQS internal absolute IDs (ID ABS). It's only needed to index into HYD binary output files (HYD Q.*.bin, etc.). In steady state, since these outputs don't exist, the mapping is unnecessary — the mesh can be built using GIS IDs directly (same logic as all other compartments).
 \end{itemize}

\subsection{Common Outputs for All Models} \label{ch:model-output}

All models within the \hydrot ecosystem must share a common output data format.  
This is required to ensure:
\begin{itemize}
    \item compatibility across models,
    \item reduced memory usage,
    \item simpler downstream analysis.
\end{itemize}
