This chapter describes the current state of \hydrot\ development: its
implementation, \texttt{HydrologicalTwinAlphaSeries} (HTAS), as the backend of
\cwv, the QGIS plugin that visualizes and analyses \cw\ outputs. It shows how
the principles of the previous chapters are put into code, and which of them
are not yet.

% --------------------------------------------------------------

\section{\hydrot\ as the Backend of \cwv}

\subsection{Overview and Motivation}

\cwv\ visualizes, explores and analyses the outputs of the \cw\ platform. As
models grow in size and resolution, the plugin needs one backend that reads
simulation outputs once and serves every dialog consistently. HTAS provides:

\begin{itemize}
    \item \textbf{Unified data access}: every \cwv\ operation goes through one \texttt{HydrologicalTwinClient}, one method per operation, on one twin per project.
    \item \textbf{A cache of simulation outputs}: \texttt{load} decodes the \cw\ binaries once into NumPy files; every later read is a cache read.
    \item \textbf{Typed results}: each operation returns a dataclass carrying its data and the paths of the files it wrote.
    \item \textbf{QGIS independence}: no module of HTAS imports QGIS or PyQt, so it runs in a script, a notebook or a shell as well as in the plugin.
\end{itemize}

\subsection{Architectural Integration}

\texttt{HydrologicalTwin} is a monolithic façade: one coherent entry point
rather than loosely coupled services.

\subsubsection{Core Architecture}

\begin{enumerate}
    \item \textbf{Data access} (\texttt{Temporal}, \texttt{services/public/temporal.py}): reading \cw\ binary outputs, the NumPy cache, observation files, temporal aggregation.
    \item \textbf{Computation} (\texttt{Operator}, \texttt{Extractor}, \texttt{Comparator}, \texttt{services/public/vec\_operator.py}): temporal and spatial operators, spatial and temporal masks, performance metrics.
    \item \textbf{Analysis} (\texttt{Budget}, \texttt{Spatial}, \texttt{polygon\_mask}): water budgets and runoff ratios, catchment cells and aquifer outcropping, selections by a polygon.
    \item \textbf{Rendering} (\texttt{Renderer}, \texttt{services/public/renderer.py}): budget bar plots, regime plots, simulation--observation plots as PDF or interactive HTML.
\end{enumerate}

Above them, the façade's \texttt{dispatch.py} routes each verb on its
\texttt{kind}, and the client's \texttt{operations\_client.py} chains the verbs
of each operation.

\subsubsection{One twin per project}

A \texttt{HydrologicalTwinClient} holds one \texttt{HydrologicalTwin}. Built
once per project (\texttt{HydrologicalTwinClient.build}), it is shared by every
operation, so configuration is read once and data are cached once.

\subsection{API Design Principles}

\paragraph{The nine macro-verbs}

\texttt{HydrologicalTwin} exposes nine macro-verbs: \texttt{configure},
\texttt{load} and \texttt{describe} for the lifecycle, then \texttt{fetch},
\texttt{mask}, \texttt{transform}, \texttt{assemble}, \texttt{render} and
\texttt{export}, each choosing its work by a \texttt{kind}. Chapter~\ref{chap-proto-hydrotwin}
lists the kinds.

\paragraph{Design rationale}

\begin{itemize}
    \item \textbf{Adaptability}: a new product is a new \texttt{kind} of an existing verb, not a new public method;
    \item \textbf{Maintainability}: internal refactors leave the verbs and their kinds unchanged;
    \item \textbf{Transparency}: an operation is an explicit sequence of verbs, visible in \texttt{operations\_client.py}.
\end{itemize}

\subsection{Implementation Status and Functional Scope}

HTAS provides the following \cwv\ operations, each a
\texttt{HydrologicalTwinClient} method:

\begin{itemize}
    \item \textbf{Water budget} (\texttt{budget\_barplot}): water-balance variables over a period, at an annual, monthly or daily frequency, as a bar plot and a CSV.
    \item \textbf{Hydrological regime} (\texttt{hydrological\_regime}): the monthly regime of discharge or head at observation points, as PNG and PDF.
    \item \textbf{Spatial maps} (\texttt{spatial\_map\_watbal}, \texttt{spatial\_map\_aq}): a water-balance or aquifer variable aggregated over a period, per cell.
    \item \textbf{Simulation against observations} (\texttt{compare\_sim\_obs}): as a PDF, an interactive HTML page, or CSV data, with separate plotting and criteria periods.
    \item \textbf{Statistical criteria} (\texttt{statistical\_criteria}): per observation point, among them Nash--Sutcliffe efficiency, KGE, RMSE, MAE, percent bias and the ratios of simulated to observed means and deviations.
    \item \textbf{Selections by a polygon} (\texttt{mask\_internal\_values}, \texttt{mask\_hyd\_boundary}, \texttt{mask\_aq\_boundary}): the values of the cells inside, the river reaches and aquifer faces on the boundary and their fluxes, optionally as GeoPackages.
\end{itemize}

\subsubsection{Performance}

\begin{itemize}
    \item \textbf{A cache on disk}: \texttt{load} writes one NumPy file per simulated parameter over the configured period, and rebuilds it only when the period changes.
    \item \textbf{NumPy first}: computations run on NumPy arrays; conversion to GeoDataFrames is deferred to the products that carry geometry.
\end{itemize}

\subsection{Frontend--Backend Separation and QGIS Independence}

\subsubsection{The layer provider}

The one thing HTAS needs from GIS is a layer. \texttt{load} asks a layer
provider for each layer by name through \texttt{get\_layer}, and receives a
GeoDataFrame (the \texttt{GeoLayerProvider} protocol). \cwv\ supplies a provider
backed by QGIS layers; \texttt{FileGeoProvider} reads the same layers from
files, which is what the \texttt{htas} command line uses.

\subsubsection{Spatial utilities}

QGIS-free spatial operations live in \texttt{tools/spatial\_utils.py}: CRS
checks and reprojection (\texttt{verify\_crs\_match},
\texttt{reproject\_polygon\_to\_match}), nearest-cell queries
(\texttt{SpatialIndex}), and reading the HYD correspondence file
(\texttt{read\_hyd\_corresp\_file}).

\subsection{Workflow Integration}

\begin{enumerate}
    \item \textbf{Detect}: \texttt{detect\_from\_out\_caw} reads a \cw\ output directory, and \texttt{detect\_project\_neighbors} the files around a QGIS project.
    \item \textbf{Build}: \texttt{HydrologicalTwinClient.build} configures and loads the twin, building each compartment from its layers and caching its outputs.
    \item \textbf{Operate}: a dialog calls one client method, which chains the verbs it needs:
    \begin{verbatim}
result = client.compare_sim_obs(
    mode="pdf",
    compartment_name="HYD",
    outtype="Q",
    param="discharge",
    ylabel="Discharge",
    obs_unit="m3/s",
    plot_period=("2000-01-01", "2010-12-31"),
    crit_period=("2000-01-01", "2010-12-31"),
    directory="/data/out",
)
    \end{verbatim}
    \item \textbf{Display}: the dialog reads the typed result (here \texttt{pdf\_path}) and shows it.
\end{enumerate}

\subsection{Steady-State Models and Missing Correspondence Files}

Steady-state \cw\ outputs are read by their own path
(\texttt{read\_sim\_steady}, \texttt{read\_obs\_steady}). When the HYD
correspondence file \texttt{HYD\_corresp\_file.txt} is missing, the HYD mesh
is built directly from the GIS identifiers, and the twin records it
(\texttt{hyd\_corresp\_missing}); HYD simulation outputs are then not readable.

\subsection{Future Developments}

Planned, and not in the code yet:

\begin{itemize}
    \item connection to an existing \hydrot\ for public access from a QGIS client;
    \item deployment on a server;
    \item a self-integrity check that marks a twin dirty when its data, its Git state or a replayed simulation disagree;
    \item the tutorials of the user guide, on the public \cw\ test case.
\end{itemize}

For \cwv's own capabilities, see its user guide
(\url{https://gitlab.com/cawaqs/gviz/cawaqsviz}).

\section{Architectural Evolution and Design Decisions}

\subsection{Monolithic Backend Refactoring}

The first \cwv\ backend had several entry points: dialogs built their own
backend objects, which duplicated cached data and I/O and made testing hard.
The refactoring made \texttt{HydrologicalTwin} the single façade, then moved
it out of the plugin into this standalone package, keeping the scientific
objects (\texttt{Compartment}, \texttt{Mesh}, \texttt{Observation},
\texttt{Extraction}) and wrapping them rather than rewriting them.

\subsection{Separation of Data Formats}

\begin{itemize}
    \item \textbf{I/O}: binaries are read into NumPy arrays, the internal data structure.
    \item \textbf{Computation}: temporal and spatial operators work on NumPy arrays.
    \item \textbf{Products}: DataFrames and GeoDataFrames are built where a product needs a table or geometry, for plots, maps and exports.
\end{itemize}

\subsection{Macro-Verbs over Helpers}

Early iterations exposed one public helper per analysis, which multiplied the
API. Public use now goes through the nine macro-verbs and their kinds. A
hydrological regime, for instance, is a \texttt{fetch} then a
\texttt{transform}:

\begin{verbatim}
values = twin.fetch(
    kind="simulation_matrix",
    id_compartment=2,
    outtype="Q",
    param="discharge",
    syear=2000,
    eyear=2010,
)
regime = twin.transform(
    kind="hydrological_regime",
    id_compartment=2,
    param="discharge",
    data=values.data,
    dates=values.dates,
)
\end{verbatim}

\subsection{The Computational Layer}

\texttt{services/public/vec\_operator.py} holds the vectorized operators,
isolated from I/O and GIS so that they can be tested on synthetic arrays:

\begin{itemize}
    \item \texttt{Operator}: \texttt{t\_transform} (temporal aggregation), \texttt{sp\_operator} (spatial reduction), \texttt{convert\_watbal\_units}, \texttt{compute\_effective\_rainfall};
    \item \texttt{Extractor}: \texttt{apply\_spatial\_mask}, \texttt{apply\_temporal\_mask};
    \item \texttt{Comparator}: \texttt{calc\_performance\_metrics}.
\end{itemize}

\subsection{The Rendering Layer}

\texttt{Renderer} (\texttt{services/public/renderer.py}) draws every figure:
\texttt{plot\_budget\_barplot}, \texttt{plot\_hydrological\_regime},
\texttt{plot\_sim}, \texttt{plot\_sim\_obs}, and the simulation--observation
reports \texttt{render\_simobs\_pdf} (Matplotlib, PDF) and
\texttt{render\_simobs\_interactive} (Plotly, HTML). It writes figures only;
data files are written by \texttt{export}.

\section{Technical Implementation Details}

\subsection{Binary File I/O and the Cache}

\texttt{Temporal} reads \cw\ binary outputs (\texttt{readSimDataFromBin},
\texttt{readSimDataFromBinSteady}), decodes them into the NumPy cache
(\texttt{decode\_and\_cache}) and reads the cache back
(\texttt{load\_from\_cache}); a missing cache raises \texttt{CacheMissError}.
Dates are NumPy \texttt{datetime64} arrays. Cells are identified by integer
identifiers linked to the GIS features, within their compartment and layer.

\subsection{Observation Data}

Observations are read from text files (\texttt{readObsData}) and attached to
the observation points of their compartment, each linked to a mesh cell. They
are fetched like simulations, and paired with them in a
\texttt{sim\_obs\_bundle}.

\subsection{Configuration}

A project is described by two configuration objects: \texttt{ConfigGeometry}
(compartments, layer names, the columns that hold cell, observation and
extraction identifiers) and \texttt{ConfigProject} (project name, \cw\ output
and observation directories, simulated years, regime). Both are built with
\texttt{fromDict} or \texttt{fromJsonFile}.

\section{Known Limitations and Development Roadmap}

\subsection{Current Limitations}

\begin{itemize}
    \item \textbf{Transitional modules}: \texttt{handlers.py} sits between the façade and the services; folding it into the verbs or the services is planned.
    \item \textbf{The catalog}: \texttt{describe} does not yet list every kind the verbs accept.
    \item \textbf{Missing HYD correspondence}: without \texttt{HYD\_corresp\_file.txt}, HYD outputs are not readable.
\end{itemize}

\subsection{Medium- and Long-Term Objectives}

Planned, and not in the code yet: calibration (self-fitting) exposed through
\cwv; a web frontend beside the QGIS plugin; multi-model and ensemble
comparison; and, in the long term, the Git-synchronised registry of Part~I,
where every visualization is linked to a provenance record and private actions
are logged.

% --------------------------------------------------------------

\section{Summary}

HTAS is the backend of \cwv: a standalone, QGIS-free Python package whose
\texttt{HydrologicalTwin} façade exposes nine macro-verbs over compartments,
with a client offering one method per \cwv\ operation and a command line.
Provenance, access control and calibration remain the work ahead.
