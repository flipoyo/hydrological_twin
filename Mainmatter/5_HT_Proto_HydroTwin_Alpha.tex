This chapter documents \texttt{HydrologicalTwinAlphaSeries} (HTAS), the public
implementation of the \hydrot\ concepts that serves as the backend of \cwv. It
is a standalone Python package, \texttt{HydrologicalTwinAlphaSeries}, in a
repository of the same name. Everything below describes what its source code
does today; the rest of this White Book describes the \hydrot\ target, of
which HTAS implements a part.

\section{Scope and Positioning}

\subsection{Role within the \hydrot\ programme}

HTAS gives operational form to four commitments of Part~I:

\begin{itemize}
    \item a single backend façade, \texttt{HydrologicalTwin}, exposed to client applications;
    \item compartments as the primary aggregate: every public operation acts on a \texttt{Compartment}, never on a mesh, an observation or an extraction point directly;
    \item typed requests and results at every public boundary;
    \item a backend free of QGIS: no module of the package imports QGIS or PyQt.
\end{itemize}

\subsection{Relationship to the full \hydrot\ architecture}

HTAS keeps the architectural grammar of \hydrot\ and implements the part of it
that public distribution allows:

\begin{itemize}
    \item \textbf{Model layer}: the compartments (\texttt{Compartment}), their meshes (\texttt{Mesh}), observation points (\texttt{Observation}) and extraction points (\texttt{Extraction}), built from \texttt{ConfigGeometry} and \texttt{ConfigProject}.
    \item \textbf{Data layer}: CaWaQS binary outputs, decoded once into a NumPy cache on disk, and observation files.
    \item \textbf{Estimation layer}: statistical criteria comparing simulation with observations. There is no calibration and no inference.
    \item \textbf{Analysis layer}: temporal aggregation, spatial averaging, water budgets, hydrological regimes, runoff ratios, aquifer balances, and selections of a domain by a polygon.
    \item \textbf{Cartographic layer}: figures (PNG, PDF, interactive HTML), spatial maps as GeoDataFrames, GeoPackage and NumPy exports.
    \item \textbf{Registry}: not implemented. HTAS persists no twin state (Section~\ref{p2c2_ssGitRec}).
\end{itemize}

Private-key authentication, parameter editing, simulation execution,
self-fitting and Bayesian inference belong to the target only.

\section{Package Architecture}

\subsection{Package layout}

\begin{verbatim}
src/HydrologicalTwinAlphaSeries/
    cli/              L0  the htas command line
    ht/client/        L1  HydrologicalTwinClient, operations_client, *Result types
    ht/developer/     L2  HydrologicalTwin, dispatch, handlers, *Request/*Response types
    services/public/  L3  Temporal, Spatial, Budget, Operator, Renderer, ...
    services/private/ L3  the NumPy and GeoPackage writers
    domain/               Compartment, Mesh, Observation, Extraction, TimeFrame
    config/               ConfigGeometry, ConfigProject, constants
    tools/                spatial utilities
\end{verbatim}

Imports point downward only: a layer never imports one above it. The command
line (L0) only collects arguments, calls one client method and prints. The
client (L1) chains the verbs of the façade, one method per \cwv\ operation.
The façade (L2) checks the lifecycle; \texttt{configure}, \texttt{load}
and \texttt{describe} act in the façade itself, and the six other verbs are
routed on their \texttt{kind} through \texttt{dispatch.py}. The services (L3)
hold the computations and the heavy I/O: reading the \cw\ binaries and the
cache, drawing figures, writing NumPy and GeoPackage files. The client also
writes the CSV and text files of its operations, the mesh reads the HYD
correspondence file, and the command line reads and writes its project
file.

\subsection{Backend façade}

The central class is \texttt{HydrologicalTwin}, imported from the package
root:

\begin{verbatim}
from HydrologicalTwinAlphaSeries import (
    ConfigGeometry,
    ConfigProject,
    HydrologicalTwin,
)
\end{verbatim}

Its constructor takes a geometry and a project configuration, the CaWaQS
output and observation directories, an optional temporary directory and
optional metadata; given both configurations, it configures the twin at once.
It creates the services it reuses, \texttt{Temporal} and \texttt{Budget}.

\section{Public Python API}

\subsection{The nine macro-verbs}

\begin{center}
\begin{tabular}{p{0.16\textwidth} p{0.74\textwidth}}
\textbf{Verb} & \textbf{Does} \\
\hline
\texttt{configure} & Attaches the configuration and the directories \\
\texttt{load} & Builds the compartments from a layer provider and caches the simulation outputs \\
\texttt{describe} & Returns the twin's description and its catalog \\
\texttt{fetch} & Reads data: \texttt{simulation\_matrix}, \texttt{observations}, \texttt{sim\_obs\_bundle}, \texttt{spatial\_map}, \texttt{catchment\_cells}, \texttt{aquifer\_outcropping\_map}, \texttt{aq\_balance\_inputs} \\
\texttt{mask} & Selects by a polygon: \texttt{polygon\_cells}, \texttt{area\_values}, \texttt{boundary\_hyd}, \texttt{boundary\_hyd\_flux}, \texttt{boundary\_aq}, \texttt{boundary\_aq\_flux} \\
\texttt{transform} & Computes: \texttt{temporal\_aggregation}, \texttt{temporal\_aggregate}, \texttt{spatial\_average}, \texttt{volumetric\_rescale}, \texttt{criteria}, \texttt{budget}, \texttt{hydrological\_regime}, \texttt{runoff\_ratio}, \texttt{aq\_balance} \\
\texttt{assemble} & Shapes a payload ready to write: \texttt{compartment\_bundle}, \texttt{boundary\_aq\_layers} \\
\texttt{render} & Draws: \texttt{budget\_barplot}, \texttt{hydrological\_regime}, \texttt{sim\_obs\_pdf}, \texttt{sim\_obs\_interactive}, \texttt{aq\_flux\_diagram} \\
\texttt{export} & Writes data files: \texttt{npy}, \texttt{geopackage} \\
\end{tabular}
\end{center}

Each verb takes either a request dataclass (\texttt{FetchRequest},
\texttt{MaskRequest}, \ldots) or the same fields as keywords, and returns a
typed response.

\subsection{Lifecycle}

\begin{center}
\texttt{EMPTY} $\rightarrow$ \texttt{CONFIGURED} $\rightarrow$ \texttt{LOADED} $\rightarrow$ \texttt{READY}
\end{center}

\texttt{configure} moves a twin from \texttt{EMPTY} to \texttt{CONFIGURED},
\texttt{load} to \texttt{LOADED}; every other verb needs \texttt{LOADED}. A verb
called too early raises \texttt{InvalidStateError}. \texttt{READY} is reserved
for consistency checks to come: no verb reaches it yet.

\subsection{A workflow}

\begin{verbatim}
from HydrologicalTwinAlphaSeries.ht import FetchRequest, TransformRequest
from HydrologicalTwinAlphaSeries.services.public import FileGeoProvider

twin = HydrologicalTwin(
    config_geom=config_geom,
    config_proj=config_proj,
    out_caw_directory="/data/OUT_CAW",
    obs_directory="/data/OBS",
)
twin.load(geo_provider=FileGeoProvider({"AQ_LAYER": "/data/gis/aq.gpkg"}))

values = twin.fetch(
    request=FetchRequest(
        kind="simulation_matrix",
        id_compartment=1,
        outtype="MB",
        param="recharge",
        syear=2000,
        eyear=2010,
    )
)
monthly = twin.transform(
    request=TransformRequest(
        kind="temporal_aggregation",
        data=values.data,
        dates=values.dates,
        frequency="Monthly",
        agg_dimension="mean",
    )
)
\end{verbatim}

\subsection{The client}

\texttt{HydrologicalTwinClient} holds one twin and offers one method per \cwv\
operation, each running a whole fetch--transform--render chain and returning a
typed result: \texttt{budget\_barplot}, \texttt{hydrological\_regime},
\texttt{spatial\_map\_watbal}, \texttt{spatial\_map\_aq},
\texttt{compare\_sim\_obs}, \texttt{statistical\_criteria},
\texttt{mask\_internal\_values}, \texttt{mask\_hyd\_boundary} and
\texttt{mask\_aq\_boundary}. \texttt{build} creates, configures and loads it
in one call; \texttt{detect\_from\_out\_caw} and
\texttt{detect\_project\_neighbors} find a project's settings from its files.

\subsection{The command line}

\texttt{htas}, run as \texttt{pixi run htas}, mirrors client methods:
\texttt{htas detect run}, \texttt{htas detect neighbors} and
\texttt{htas describe}. The twin is read from an \texttt{htas.toml} project
file, which \texttt{htas detect run} can write, and options override it.

\section{Persistence and Public Reproducibility}

\subsection{What the public series persists}\label{p2c2_ssGitRec}

HTAS does not serialize a twin. A twin is rebuilt from its configuration at
each session. What reaches the disk is:

\begin{itemize}
    \item the NumPy cache that \texttt{load} writes for each simulated parameter over the configured period, rebuilt when the period changes;
    \item the files the operations write: figures from \texttt{render}, NumPy arrays and GeoPackages from \texttt{export}, and the CSV and text files of the client operations.
\end{itemize}

The code itself is identified by its version: HTAS follows Semantic Versioning
since \texttt{1.0.0}, and every commit and release is named after it. The
Git-synchronised registry of the target (Part~I) is not part of HTAS.

\section{Integration with \cwv}

\cwv\ carries HTAS as a Git submodule, at
\texttt{external/HydrologicalTwinAlphaSeries}, and installs it at the
plugin's first launch. The plugin calls HTAS only through
\texttt{HydrologicalTwinClient}, and supplies the layer provider that turns
QGIS layers into GeoDataFrames; outside QGIS, \texttt{FileGeoProvider} reads
the same layers from files. The separation defended in this White Book is
therefore in the code:

\begin{itemize}
    \item \cwv\ is the visualization client;
    \item \texttt{HydrologicalTwinAlphaSeries} is the scientific backend;
    \item the \hydrot\ programme remains the conceptual and authenticated superset.
\end{itemize}

\section{Conclusion}

\texttt{HydrologicalTwinAlphaSeries} is the current public implementation of
\hydrot: a standalone Python backend whose \texttt{HydrologicalTwin} façade
exposes nine macro-verbs over compartments, with a client for \cwv\ and a
command line on top. The complete \hydrot\ target remains the authenticated,
calibration-capable digital twin framework described in the rest of this
White Book.
